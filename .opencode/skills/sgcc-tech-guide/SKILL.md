# 国网总部科技项目指南编制

按证据顺序工作：先确定范围和范例基线，再完整阅读资料、形成综述和课题设计，最后写指南。不得从模型常识补造术语、方法、系统名称、工程事实或验收阈值。

本 Skill 运行在能元隔离工作目录中。必须先建立本次任务子文件夹，再把全部成果写入该文件夹。

## 任务子文件夹（强制）

当前工作目录是会话隔离目录，根下只允许：

- `INDEX.md`、`TASK.md`（系统准备，只读参考）
- `literature/`（用户附件，只读）
- `refs/`（本 Skill 参考副本，只读）
- `.opencode/`（系统链接）
- `./<任务名>/`（**你创建并写入的唯一成果根**）

规则：

1. 先读 `TASK.md` 与 `INDEX.md`。任务名优先用其中的「建议任务名」；若已能确定正式项目短名，可用清洗后的项目名。
2. 用 `write` 创建 `./<任务名>/00_项目总体/01_输入与范围/范围说明.md` 作为第一份落盘，等于创建任务文件夹。
3. **全部中间成果和正式成果只写在 `./<任务名>/` 内。** 禁止写到工作目录根、`literature/`、`refs/`、`knowledge-corpus/`。
4. 非法字符（`\/:*?"<>|` 和控制符）必须去掉；名称不超过 40 个汉字或字符。
5. 生成正式项目名后若需重命名任务文件夹，先把内容写到新名目录，不要把旧文件留在根目录。
6. 每完成一个阶段立刻落盘，不要等全部写完再一次性输出。

## 必读资源

开始任务后**先只读这三份**，读完立刻扩写范围说明并按预检索命中写盘。其余 `refs/` 写到对应章节时再读，禁止把全部参考读完再检索：

- `refs/v7-required-deliverables.md`
- `refs/dense-single-document-summary.md`
- `refs/corpus-hits.md`（工作区预检索命中；没有则再 grep `knowledge-corpus/papers`）

需要体例、证据系统或固定母版时再读 `writing-style-and-examples.md`、`evidence-system-and-incremental-build.md`、`fixed-guide-format.md` 等。

处理用户附件时用 `read` / `grep`。知识库优先 read `refs/corpus-hits.md` 列出的路径。若仍需 grep，path 只能写 `knowledge-corpus/papers`、`knowledge-corpus/patents`、`knowledge-corpus/books`（基金/项目才用 `knowledge-corpus/projects`）。禁止 `patents/patents`、禁止 `../../knowledge-corpus`、禁止 glob `*`、禁止枚举语料根、禁止 `knowledge-corpus/mentors`。同一路径失败一次立即换分域或 `web_search`，禁止反复重试。`read` 不会被截断，读多少由你根据证据需要自行决定。有文献包时先读 `literature/extracted/INDEX.md` 与 `01_全文提取`。

## 产品化输入（允许构想启动）

用户构想 + 知识库检索 + 创建时附件，即构成正式指南的范围依据。不要因为缺少「个人研究方向」独立文件而停止或只做资料清点。

范围优先级：

1. `TASK.md` 中的用户构想与本轮修订意见
2. `literature/` 附件与 `literature/extracted/` 全文抽取
3. 知识库检索到的论文、专利、项目与标准线索
4. 联网补证（`web_search` / `webfetch`）

若存在原稿（`原稿.md` 或 `literature/extracted/manuscript.md`），主交付是按文献证据重写第一、二章，写入 `05_正式成果/重写稿.md`，七段指南为附加成果。

不预设课题数；根据构想与证据设计 3—5 个递进课题。无可靠规划编号时写「建议新增（待赋号）」，不得虚构已有编号。

## 强制工作流

1. **确认输入和范围。** 读取 `TASK.md`、`INDEX.md`、`literature/`。任务文件夹若已预创建，立刻扩写范围说明；否则先创建任务子文件夹再写范围说明。不要把全部 refs 读完再动笔。
2. **检索与阅读。** 对 `knowledge-corpus/papers`、`knowledge-corpus/patents`、`knowledge-corpus/books` 检索核心术语，read 命中全文。有 `literature/extracted` 时优先读抽取全文。必要时 `web_search`。然后进入资料清点与三类总结。
3. **建立当次范例基线。** 不要求本地「国网范例」目录。以 `refs/` 中的固定体例与知识库中相近总部科技项目/指南为当次基线，输出《最新范例写作基线与重复边界》。不得把某一历史样例的技术内容写进本项目。
4. **处理旧稿但不依赖旧稿。** 若任务文件夹或附件中有旧稿、标黄、批注，逐项吸收；无则跳过，不得虚构「V2问题清单」。有原稿时，主交付是按证据重写第一、二章，写入 `05_正式成果/重写稿.md`。
5. **资料清点、分类和去重。** 为附件、库内命中和网络补证分配资料 ID。哈希完全一致才算完全重复。同一资料可归入多个课题，只维护一份主记录。
6. **按文种阅读和单篇总结。** 对实际拿到的资料执行分类提取与高密度总结。附件已转为 Markdown 时可直接阅读。库内条目用 `grep` → `read`，不要假装读过未打开的文件。资料不足时写清缺口，仍可基于已有证据继续课题设计，并在指标中标注「建议值，需标定」。高密度必须正式中文题名 + 核心结论 + 恰好 5 个二级专章，不少于 1500 汉字；复杂资料可以更长。禁止页眉、基金项目或题录切片。
7. **主动联网补证和标准换版检查。** 对正式结论依赖的标准、专利和关键公开技术做网络核验。候选网络资料使用 `NET-xxx`。编造网址或文献视为失败。
8. **建立结构化证据系统。** 按 `evidence-system-and-incremental-build.md` 写原子证据、覆盖矩阵、三类映射、指标卡。Markdown / JSON / XLSX 从结构化数据派生。
9. **先综述后设计。** 形成单课题综述、研究空白和三个递进研究点，再写单课题指南。
10. **术语和工程边界门禁。** 标题、关键技术和指标只允许 N/A 级核心术语。通用信息技术只能作为电网对象问题的支撑工具。
11. **先课题、后总体。** 每个课题写成「标题 + 一段预期目标 + 三段考核指标」。功能需求、关键技术与课题按相同顺序一一对应。
12. **指标需可验收。** 先写指标卡。文献算例不得直接当作项目指标；证据不足时用成果型指标或标注待标定。
13. **固定母版成稿。** 将指南整理为 `scripts/build_fixed_guide.py` 规定的 JSON，写入任务文件夹（建议 `05_正式成果/guide.json`）。优先运行该脚本和 `assets/sgcc-guide-fixed-template.docx` 生成 DOCX。不得从空白 DOCX 重建，不得用表格承载指标。若本环境无法运行 Python / LibreOffice，必须先写好 JSON 与 Markdown 正文，并在质量报告中注明「DOCX 待宿主生成」。
14. **分层、增量交付。** 按 `v7-required-deliverables.md` **一次性逐一**写完必须成果：唯一详细版/高密度V7/一页版、各课题综述—设计—指南—证据映射、决策版综述、两类汇编、详细证据、台账源数据和质量报告。禁止生成 V6 历史副本、`page-*.png`、contact sheet。PDF 与逐页渲染为尽力而为，不作为本环境完成门禁。缺一项不得宣称完成。

## 核心写作顺序

```text
创建任务子文件夹
  -> 最新范例基线与重复边界
  -> 课题范围与资料总清单
  -> 分类阅读、高密度单篇总结
  -> 网络补证与标准版本核验
  -> 原子证据、准入评分、覆盖缺口和三类映射
  -> 工程矛盾、研究空白、项目增量和指标卡
  -> 单课题综述与术语校核
  -> 三点式课题设计
  -> 单课题指南与证据映射
  -> 跨课题冲突消解
  -> 总指南及决策版/一页版/详细证据分层成果
  -> 固定母版 JSON / DOCX 与质量报告
```

应用场景写“背景事实 -> 既有做法 -> 具体矛盾及工程后果 -> 应用对象”；功能需求写业务能力，不提前塞入算法；关键技术按课题顺序写对象和研究动作；每个课题写“机理/模型 -> 核心方法 -> 工具/方案/验证”；成熟度按成果分别给出攻关前后等级和验证环境。

## 固定建议稿输出

1. 完整读取 `refs/fixed-guide-format.md`。
2. 将指南内容整理为 `scripts/build_fixed_guide.py` 规定的 JSON；功能需求项数、关键技术项数和课题数必须相等。
3. 用固定母版生成 DOCX。每个课题始终占 5 个连续段落：标题、预期目标、指标（1）、指标（2）、指标（3）。
4. PDF / 域更新 / 逐页检查能做则做；做不到时以 JSON + Markdown + 质量报告为准，由宿主补生成 DOCX。
5. 能运行 `scripts/check_guide_docx.py` 时必须运行；不能运行时在质量报告中记录。

## 停止条件

出现下列情形时，不得宣称「正式终稿已完成」，但必须把已完成的中间成果留在任务文件夹并说明断点：

- 标题或指标含 P/X 级核心术语且未改掉；
- 指标阈值无依据且未标为待标定；
- 跨课题研究对象、方法或成果接口存在未解决冲突；
- 指南 JSON 缺少固定骨架字段，或功能需求 / 关键技术 / 课题数量不一致。

下列情形**不再**作为停止条件：缺少单独的研究方向文件、本地没有国网范例目录、未能导出 PDF、未能逐页渲染。

## 公开回复

最终对用户的公开回复只用简短中文说明：任务文件夹名、课题数、已写入的关键路径、未完成项。不要把过程推理、工具日志或整份指南正文贴进对话。
